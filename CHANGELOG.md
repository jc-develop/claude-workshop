# CHANGELOG

## [Unreleased]

### Fixed

- Reading a single email log now takes an admin, the same rank its listing has always taken. `EMAIL_LOG` records who was written to and at what address, and the table is reachable only through the service role, so the floor named in the handler is the whole of the gate. The listing asked for an admin; the detail route one path segment below it asked for a facilitator — a rank that cannot open the listing at all. Because the id in that path is a bare integer with no ownership test, a facilitator could count upwards through it and read, one record at a time, precisely the rows the listing declines to show them.

- The speaker pages no longer jump as they load, and they were the worst two in the app. Each answered a request in flight with one line of centred text under the rail, then replaced it with a page the better part of a thousand pixels taller: 0.357 on the engagements list and 0.359 on an event, more than three times the budget. Both now hold their own shape while they wait — the list around the same card-grid skeleton the attendee list already uses, since what arrives is the same grid of event cards, and the event page around its own twelve-column layout, whose 400px hero card is most of the height at stake. The course builder was over-reserving in the other direction, having borrowed the listing pages' eleven rows for a page that settles some 240px shorter.

  Measured per route, before and after: `/speaker/events` 0.357 → 0.055, `/speaker/events/[id]` 0.359 → 0.003, and its course builder 0.064 → 0.001.

- Staff pages no longer jump as they load. The content sat full-width on the first paint and then slid 72px right when the collapsible rail appeared, because the shell decides whether to reserve that space from the signed-in role — and the role arrives a round trip after the page is already on screen. That one shift measured 0.047 on every staff route and was the largest single source on all seven. The width is now held open by the route: these prefixes are staff surfaces, so the space a rail will occupy is reserved before the session answers. Reserving it is not the same as rendering it — the rail itself still waits for the role, so a visitor without it is never shown the console's navigation on their way to being redirected.

  Underneath that, two loading states were standing in for far more than they occupied. A staff page waiting on its role guard showed one centred line, and a table waiting on its rows showed a single spinner about a tenth the height of the rows it replaced — so the page grew twice, once by roughly 250px and again by roughly 430px. Both now hold open something close to the height that is coming: eleven rows, which is measured rather than guessed, being what five of the seven staff pages settle at exactly. The tickets list had the same one-line loading state and is fixed the same way.

  Measured per route, before and after: `/staff/audit-logs` 0.138 → 0.001, the other six 0.082–0.093 → 0.001–0.007, and `/tickets` 0.057 → 0.024.

- The event detail page no longer jumps as it loads. It rendered one line of centred text while its data was in flight, which let the app shell's `mt-auto` footer sit mid-viewport; the arriving page then pushed it back down in a single 0.425 layout shift — four times the 0.1 the Lighthouse budget allows, and effectively the whole of that page's CLS. It now reserves the page's actual shape while it waits: the same `max-w-page` gutters, the same two-column split, the same cover height, and an aside roughly the height of the register card that decides where the footer lands. Measured 0.426 before, 0.001 after.

  The course library had a milder version of the same thing at 0.062, and is fixed the same way. Both loading states are now built from one shared `Skeleton`, which is also what the events list skeleton is made of — the fill and the pulse are one decision rather than a shape copied between modules, and the layouts stay next to the pages whose height they have to match.

- Searching the events list no longer flickers on every keystroke. Two things were moving that should not have been. The rows dimmed while a refetch was in flight and undimmed when it landed, so each character faded the whole grid down and back up — and the slower the answer, the more of it, which is backwards for a progress signal; the rows are now left alone entirely and a spinner appears in the search box instead, a quarter second in, so a fast search draws no indicator at all. And the entry animation replayed on the way back: typing only removes cards, but deleting a character re-matches events, React mounts their cards afresh, and mounting is what starts a CSS animation — so every backspace rose the grid again, and returning from a term that matched nothing rose all of it. The animation now belongs to the list's first arrival and ends the moment the reader touches the search box or the tabs.

- Deleting a user no longer reports a phantom failure when the auth identity is already gone, and the roster no longer keeps a tombstoned row on screen until a reload. The admin delete ran the teardown to its last step — the auth identity — and treated GoTrue's "User not found" as a hard failure, so an account without a live auth row (a directly seeded user, say) threw even though every purge and the profile tombstone had already landed, and the error branch skipped the roster refetch, leaving the deleted row visible until a manual refresh. The teardown now treats an absent identity as the goal reached, using the same 404 / "user not found" tolerance the password-reset link already applies, and the delete dialog refreshes the list even when a teardown step reports an error, so the table always mirrors the server.
- The speaker dashboard now loads live and upcoming engagements. `useSpeakerEvents` marked a tab as loaded before its fetch started, so the StrictMode double-mount discarded the only in-flight request and the page sat on "Loading engagements..." forever; the tab is now flagged loaded only once the fetch settles.
- Anonymous callers on the support and staff routes now get `401 Unauthenticated` instead of `403 Forbidden`. Four routes folded the role floor into the session null-check, so a logged-out caller earned the "Forbidden" reserved for the authenticated-but-unpermitted — the pairing RFC 9110 rules out and `guardFailure` was built to prevent. The role-floor routes now run through `requireMinRole`, which answers unauthenticated with 401 while keeping every permitted denial a 403. Routes that authenticate without a floor (`support`, `sessions`, course rooms, `live/highlight`, `auth/me`) keep their capability predicates but report a missing session as 401 too.

### Changed

- The community hero's copy arrives a line at a time, as the landing hero's does. The two sit under the same navbar and are cut with the same foot, so one of them appearing all at once while the other rose in read as an oversight rather than a distinction. It reuses the landing page's `hero-rise` — no new animation, and no JavaScript: the hero is a server component and the entry is two class names.

  The photograph is deliberately left out of it. It is the page's largest paint, and Chrome does not count an element as painted while it is still transparent, so fading it in would push LCP back by the length of the animation. The text over it costs nothing by the same measure.

- Paging the events list no longer collides with searching it. A Load More still in flight when a search or a tab landed appended its rows underneath the new results, so a page of events nobody had asked for sat below the ones they had — and the totals came back describing a listing that was no longer on screen. Every request now carries the listing it was sent for and is discarded if that listing has been replaced, which covers pagination and the first page alike; the first page had been guarded, but the guard lived in an effect's cleanup and pagination has no cleanup to hang one on.

  A page that fails is also retried rather than skipped. The cursor moved before the request rather than after it, so a failed page two left it on two and the retry asked for three, putting page two's events out of reach until the page was reloaded.

- Switching tabs on the events list stops flashing "No events found." The rows on screen were filtered again in the browser by status, left from when the tabs were one page of fifty split three ways. The tab changes on the click while its events are still being fetched, so every row on screen failed the new tab's test at once and the grid emptied for a round trip before the archive arrived. Each tab has been its own query for a while now, which makes that second filter redundant as well as destructive — the previous tab's rows now stay up and dim, exactly as a search's do.

- Cards on the events list settle rather than snap. Three things moved that should not have. A card's accent gradient was picked by its position in the grid, so a search that removed the rows above one recoloured it — the card that survived the search was the only thing on screen that moved; the accent now follows the event's own id and stays put. Rows that genuinely are new fade and rise in, staggered, and only they do: a card is keyed by its event, so one that survives a refetch keeps its element and is left alone. And the grid is left entirely alone while a refetch runs, down to its opacity; the wait is reported by a spinner in the search box instead, held back a quarter second so a search the server answers quickly draws nothing at all.

  The motion is behind `prefers-reduced-motion`, with the visible state as the rest state: written the other way round, a reader who has asked their system for less movement gets cards that never arrive.

- `/events` and `/community` render their first screen on the server. Both routes were a one-line re-export of a client component, so a visitor waited out four steps before seeing anything — the HTML, the JS bundle, hydration, and only then the request for the rows. The landing page has always fetched its events server-side, and that was the whole of why it felt faster than the other two for the same data. Each route now fetches through the same service call its API route uses, session included, so the seed is scoped exactly as the endpoint would have scoped it.

  `/community` was the slower of the two because it fired two independent requests and could not finish painting until the slower one landed. They are one `Promise.all` on the server now. Its memories strip also gets placeholder cards while it loads, rather than a gap that pushes the footer down when the real ones arrive.

  The hooks still own everything after the first paint: a tab, a search or a reload fetches exactly as before, and a hook handed no seed behaves as it always did — which is what the staff pages rely on. The skip is keyed on which query the state currently answers rather than on a first-run flag, because React mounts a tree twice in development and a one-shot flag is spent by the pass it throws away, leaving the real one to refetch everything the server had just sent.

- Each tab of the events list fetches its own events. The tabs were a filter applied in the browser to a single page of fifty rows, so a tab showed only the events of its kind that happened to fall in those fifty — put fifty upcoming events on the books and Completed rendered empty with the entire archive sitting behind it, reachable by nothing on screen. Every tab is now its own query, with its own pagination, and Load More walks that tab rather than the undifferentiated list.

  Upcoming and Completed ask for a window on the calendar rather than a status, because a past event that nobody has published as finished still reads as complete — the status column is only advanced by hand, and the read path derives the truth from the end time. Asking for `status=complete` would have missed exactly those. Drafts is the one tab that really is a status, since a draft sits on either side of today.

  The count beside a tab now comes from the server's total for that tab, so it counts the whole of it rather than the page that happens to be loaded. Only the open tab carries one: each tab is a separate query, so a number beside a closed tab would be a count of something nobody had asked for.

- Searching the events list no longer flickers. Each keystroke replaced the results with six skeleton cards and then put results back, so the grid unmounted and remounted on every search and the page resized as it went — the skeleton is a fixed six placeholders and a result set is whatever matched. The rows a search is replacing now stay on screen and dim while the new ones load, which is the treatment the staff tables already gave their rows through `TableBody busy`. The skeleton is the cold start only, where there genuinely is nothing to show yet.

  The distinction is a first page having ever landed, not the list being non-empty — keyed off row count, a search that matched nothing would arm the skeleton again for the very next keystroke, putting the flicker back exactly where the search gets narrowest.

- The events listing stopped fetching columns nothing renders. The query behind `/api/events` selected `*` and the whole row went to Postgres to serialise, the Worker to parse and re-serialise, and the client to discard — `description`, `price`, `currency`, `survey_enabled` and the timestamps among them. It names its columns now.

  `meeting_url` is one of the columns it no longer asks for, which turns a redaction into a structural guarantee. The listing feeds the public event list and the landing page, so a link selected there reaches anyone who can see an event at all; the service used to strip it off each row on the way out, and that held only while everyone remembered it was there. The row type has no such field now, so nothing downstream can read one.

- Role and status pills are legible. The label had been the same hue as its own fill at a different strength, which on white measured 1.97:1 for `warning` and 2.73:1 for `success` against the 4.5:1 that text this size needs — the pill read as a solid lozenge with something written in it. Labels now take the muted foreground the surrounding secondary text already uses, over a fill at double the tint, which clears the line on every variant.

  Dark mode takes the full foreground instead. Its muted foreground clears AA against the bare surface by 4.81:1 and has nothing left to give, so the same tint underneath put all four variants back under the line — the fix for one theme was a regression in the other. A pill also no longer wraps: `Super Admin` is the only role name of two words, and in the organization table it broke across two lines, which turned the rounded pill into a lozenge that sat crooked against its row.

- The staff page that manages staff became one that manages users. The roster now lists every account — not just the staff tier — with **All users** the only way to widen the default **Staff only** filter, and tombstones no longer surface in it. The page and its API moved from `organization` to the name of the thing they act on, so the trail says "user" everywhere it used to float "organization": `/staff/users`, `/api/users`, and audit entries that read `user.*`.

- Admins can now delete a user from the staff users page, and the delete is the same account teardown the user runs on themselves: every row they own is purged, the profile scrubbed, and the auth identity removed. The old bare `window.confirm` is gone — the action is gated to roles the actor strictly outranks (so nobody deletes the caller's own row or a peer admin) and confirmed in the shared account-deletion dialog, which warns the purge is permanent before a single request is sent.

- **Breaking wire shape.** Every domain failure now answers the flat `{ error: "…" }` body the auth guards already serve, instead of three drifting shapes. `community/*`, `organization/*`, the `events` collection, `events/[id]` (its 400/500 branch) and `modules/[id]` (its 400 branch) used to answer nested `{ error: { message } }` — or split flat/nested by status — because each route hand-rolled a `mapError` next to its service. Twenty copies and five inline blocks collapsed into one `toErrorResponse` helper over a single shared `ServiceError` base, so a route can no longer render the same failure two ways. The client reads both shapes through `apiErrorMessage` while the flat body rolls out.

- Every authenticated-only API route now guards through the same `requireRole()`/`guardFailure()` pair the role-floor routes already used. The app used to answer "who is calling?" two different ways — a hard guard on routes with a role floor, and a soft `requireAuth()` plus inline identity checks on routes that only needed to know the caller was signed in — so the same question had two APIs and a refusal's shape depended on which dialect the route happened to be in. That was the bug: the soft dialect answered a caller with no session with `403 Forbidden`, so clients could not tell "log in" from "you may not do this" without special-casing the route.

  The guard is now only the authentication door: it returns the caller or a `401 Unauthenticated`, and the entitlement checks that cannot be stated as a role floor (edit, publish, survey, attendees, meeting_link) stay in the capability paths where they belong rather than being spelled out as ad-hoc role tests. The handle functions read `guard.user`, so ownership and audit code has one canonical source of truth for the caller's identity.

  Three converted routes had no guard coverage at all and now carry their own 401-and-no-lookup tests.

- The top navigation bar is taller, its links a step larger, and it is frosted rather than solid. At 64px with 14px links it read as chrome to get past; it now stands at 72px with 16px links, and the page scrolls under it through a translucent, blurred surface instead of behind an opaque band. SIGN IN keeps its 14px deliberately — it is the one control up there that is not navigation, and it was already carrying that distinction in its caps and letter-spacing rather than in its size.

  The staff bar matches it — same height, same frosted surface — which meant moving the collapsible rail down with it, since the rail hangs off the bar's bottom edge and sizing one without the other opens a gap down the left of every staff page. Both now read the height from the token instead of naming a number, and the content offset went back to being one value rather than one per bar. The surface itself is shared between the two bars rather than spelled out twice: the alpha and the blur are one decision, since translucency is what lets the page through and the blur is the only reason the links stay readable over it, and half that pair copied into a second bar is a bar you cannot read.

  The height is a token now (`--spacing-navbar`) because it was never one number: the bar sets it and the content below sets its own top padding to clear it, in a different file. Those two had been kept in step by hand, and the padding was shared with the staff bar, which is a different bar of a different height — so raising one would have pushed a band of dead space onto every staff page. Each now clears the bar that actually rendered above it.

- The landing page's Upcoming Events strip shows three events instead of two. The grid it renders into is three cards wide from the `lg` breakpoint up, so asking the query for two left every desktop visitor looking at a row with a hole in it. The limit is now named after the thing that decides it rather than sitting in the query as a bare `2`, since the next person to widen the grid needs to find it.

  Three is still a strip rather than a listing, so the section heading now carries **See all events** through to `/events` when there are more upcoming events than fit. It appears only when it leads somewhere: the query reports how many upcoming events exist in total alongside the handful it returns, and a link that would land on the same cards the visitor is already looking at is worse than no link. Before this the strip was a dead end — publish a dozen events and nine of them were unreachable from the front page, with nothing on screen to suggest they existed.

- Account settings is one card per concern, each with its own save, on the same wide column every staff page uses. It was a single 896px form with one **Save Changes** at the foot, which meant the button did whatever happened to be dirty — a press could rename the account, mail a verification link and change the password in one go, and the confirmation afterwards had to work backwards from which combination had landed to decide what to say. Nothing on screen told you which of the three a press was about to do.

  Each card now owns its action and says what it does: **Save profile**, **Send verification link**, **Update password**, **Save professional info**. A card is its own `<form>`, so Enter saves the section the cursor is in and nothing else, its button lights only when that card is dirty, and the confirmation appears in the card that earned it. One guard still spans them all, so two sections cannot race the same session. This is the shape GitHub, Stripe and Vercel settle on, and the reason is the same: these are different operations with different consequences, and one is not a batch of the others.

  The page also moved onto the shared `StaffPage` frame and now lays out exactly as the staff event page does: full-width panels stacked in the 1360px column, no side rail. Settings was the one signed-in page on its own narrower 896px column, which made moving between it and the rest of the app a visible change of shape. The cards are `SectionCard` — the same panel the event page renders, rather than a second definition of it, which that component's own note warns about after the event page grew two and they drifted apart. The extra width is spent inside the cards, on field grids that go two and four across, rather than on one long ladder of inputs. Delete Account keeps a card but no save button, so a destructive action never wears the same control as the ones above it.

  Underneath, the label/input/message/ARIA quartet that was spelled out at fourteen fields is one `TextField`, which derives the `aria-describedby` ids from the field's own id — a field can no longer be labelled without being described, or point at a message that is not on the page. The four speaker links were four state pairs, four editors and four entries in both the validation loop and the rendered list, differing only in a label and a placeholder; they are one table now. The page component went from 131 lines to 57, and the merged `profile-name-section` is gone.

- The staff event page is one page now, rather than a page with another page rendered inside it. Editing an event lived in a panel on the Overview tab, and the form it put there carried its own page frame — its own background, its own measured column, its own `<h1>Edit Event</h1>` and its own "Back to Event" link, all sitting inside a card that was already inside the event page. That frame had been invisible while `/staff/events/new` was the only place the form was used, because there it _was_ the page. Page chrome now belongs to the route: the create page supplies its own heading and back link, and the form renders nothing but its fields, so the same component can sit in a panel without claiming to be a page.

  Overview stops being the tab that holds everything. It is a read-only summary — the stats, the description, what the event is, and the delete — and the things that were stacked underneath it have tabs of their own: **Details** edits the event and holds its cover image, **Team** staffs it. Publish, the kiosk and the course room were each buried inside whichever panel happened to own them, and none of them belongs to a panel, so they now sit above the tabs as the event's own actions. The Kiosk tab is gone with them, having only ever contained one button pointing somewhere else.

  Facilitators and speakers were assignable in three places at once: as a section of the edit form, as a pair of tables beside it that wrote immediately, and on a separate unstyled `/staff/events/[id]/speakers` page nothing linked to. An admin had no way to tell which of the three the roster on screen came from, or whether adding someone there needed a Save afterwards. There is now one surface per context — the create form carries the roster because there is no row to assign against until the POST returns, and an event that already exists is staffed from the Team tab, where each add and remove is its own request and nothing waits on an unrelated field to validate. The orphaned `/speakers` page is deleted, as is `/staff/events/[id]/edit`, which nothing had linked to since the list's Edit button started pointing at the event itself.

  Saving under Details stays on the page. It used to navigate to wherever it came from, which — once the form moved onto the event page — was a redirect back to the URL you were already on, whose only visible effect was losing your place. Save is now held until something has actually changed, Discard restores what is stored, and the hero above the form follows the save without refetching it. Two rosters were being fetched twice over on arrival, once by the embedded form and once by the tables beside it; each is now owned in one place, and the speaker roster — which every staff member paid two requests for, including facilitators who cannot see it — is not loaded until the Team tab is opened.

  One bug came out of the seams: an event's stored `start_time` arrives as `09:00:00` while the time input holds `09:00`, so a form seeded from a saved row and then read back compared unequal to itself. Times are trimmed where the row is widened into form values, and the form tracks what it has saved rather than trusting the spelling the server echoes back.

- A module in the curriculum builder is now edited behind **Edit** and written by **Save**, and nothing in between reaches the database. Every control used to write the moment you left it — a lesson name committed on blur, a description on blur, a session window the instant its pair was complete, a speaker on selection — so the state of a module was a question of which field you had touched last, a half-finished edit had no way back, and the only way into a lesson's fields was a 14px pencil you had to discover. The Save button people went looking for did not exist, because there was no editing session for it to belong to. Pressing Edit opens the module: its name, session window, speaker, and every lesson's name, description, order, file and link become editable together, and each change accumulates in a draft. Save then works out what actually differs and writes it as one ordered batch — deletes and material drops before creates and uploads, so a lesson can shed one file and gain another in the same save without the drop landing on the new url. A change typed and then undone produces no request at all, and Cancel discards the draft for free. One module is editable at a time: a draft spans a module, and two open at once would let one Save look as though it had covered both.

  While a module is open its lesson fields are plain inputs rather than click-to-edit. That is the point — an edit affordance you have to find is what went unfound, and Edit has already said what mode the module is in. A file picked for a lesson is held in the browser and uploaded after Save, because an upload posts against a lesson id and a lesson that does not exist yet has none; if that upload fails the lesson has already been created, so the message says so rather than implying the whole save was lost.

  Reordering a lesson inside its module is part of the draft. Moving one to a different module cannot be, and keeps writing straight through — from a **Move to…** picker on the read-only rows — because the destination has not opted into an edit and no Save of the source could ever cover it. Q&A modules are not offered as destinations.

- Course material opens in an overlay instead of a new browser tab. PDFs, images and videos render in place from the same entitlement-checked storage route they always used, and an external link is framed there too, with **Open in new tab** always available and a note on links that some sites refuse to be embedded — many send headers that leave the frame blank with no error of their own. A lesson's material can also be detached from the module editor: **Remove material** marks it, and Save deletes the stored objects outright and clears the lesson's `content_url`, so a different file can take its place. That deletion is permanent by design.

- Every staff page now sits in the same column, and it is wider than most of them were. The nine of them — events, the event detail page, organization, community, emails, support, audit logs, the profiler, and the facilitator's own event list — had each hand-rolled the frame around their content and drifted into four maximum widths across five paddings. The event pages stopped at 1360px; audit logs, emails, support and the profiler at 1024px; organization 128px short of that; community and the facilitator's list had no maximum at all, so their content stretched to whatever the display was while every neighbouring page stayed in a measured column. Titles had drifted the same way, from 16px on community to 36px on events, and only four of the nine carried a line saying what the page was for.

  All nine now compose one `StaffPage`, measured to a new `--container-page` token. The width is the event pages' 1360px rather than the narrower column most of them used, because that was the one number among the four that had a reason behind it: a non-attendee opening `/events/[id]` is redirected to the staff view of the same event, so the two are one journey and were deliberately matched. Narrowing to anything else would have broken that pairing to fix this drift, and the public page now reads the same token, so the two cannot come apart again. The events page loses the icon tile beside its title, which no other page had.

  Three things came out of the frames along the way. The facilitator's list had titled itself with a `<span>`, so one of the two pages that role can reach had no heading for a screen reader to navigate by, and every page now has exactly one `<h1>`. The loading and error states scattered through these pages reached for `text-muted-foreground` and `text-destructive`, and the event detail page's tab strip for `text-foreground` — none of the three is a token in this theme, so Tailwind emitted no rule and the text took whatever colour surrounded it, including the tab marking which one you were on. All now use tokens that exist. And the Create Event button asked for `text-white` rather than the token that means the same thing, which is the sort of thing that breaks the day the brand colour moves.

- An admin can now change an existing member's role from the organization page, attendees included. The role a person holds was decided once, at the invitation, and never afterwards: an attendee who later agreed to facilitate could not be made one, because inviting their address is refused — Supabase already holds an account for it — and the roster only ever listed staff, so there was nobody to click. A role picker now sits in the member drawer, and the roster reaches past staff to find the person it is about: searching by name or address looks across every role, and the filter offers Attendee alongside the rest. The default list is still the staff roster, since attendees outnumber it by orders of magnitude, and it now opens ranked by authority — super admins first, then admins, facilitators and speakers, alphabetical within each — rather than alphabetically across all four, which had opened the page on whoever happened to be first by name. A search is ranked the same way; a list narrowed to one role stays alphabetical, having nothing to rank. Demotion works the same way — facilitator back to attendee is just the picker run the other direction — and the audit row records the role that was replaced as well as the new one, which the request itself does not carry.

  Two things are refused. A super admin's role cannot be changed and a super admin cannot be removed, by anybody, including another super admin: that role decides who else may hold `admin`, so leaving it editable here would make it assignable in effect — demote the holder and the seat is open to whoever asked. It is granted in the database, deliberately. Nobody can change their own role either, which would take away the page they are standing on along with the account that could undo it.

  Granting `admin` still needs a super admin, but that is no longer written as a rule about admins: you may hand out only a role you outrank, which says the same thing about every role at once and is now asked in one place instead of four. The invite form, the role picker and both write paths had each carried their own copy, and a copy that disagrees is a picker offering what the server refuses. The pickers ask the same question the routes do, so the answer arrives before the request rather than as a failed one.

- The navbar now says where you are with a line instead of a fill. The top bar's navigation links draw a brand underline flush with the bar's bottom edge on the current page, and the staff rail trades its brand-tinted pill for a full-height, square brand line flush with the rail's outside edge on the active item. Those markers had to be read against the bar's or rail's own background before you could tell the current page apart, so blue is now reserved for the selected entry alone — grey undertones do the rest, no other thing in either bar uses the brand colour. Idle links sit lighter than the foreground (`text-muted-fg` at reduced opacity) and hovering a non-selected entry darkens them to the full foreground, while the selected entry carries no hover rule and stays blue; hovering previews no line in either bar. The heavier weight and `aria-current="page"` still state the current page outright, and no nav link keeps a background fill.

- The forgot-password form now tells you when the address you typed has no account. It used to accept every address alike and answer "check your inbox" whichever one you gave it, so somebody who mistyped their own address got the same screen as somebody who had not, and learned nothing until the mail never came. It now looks the address up and, when there is no account behind it, keeps you on the form with the address still in the field and the field marked in error — "This email is not yet registered. Check the spelling, or create an account." A backend outage is reported separately and never as a missing account, so Supabase going down cannot tell every visitor in turn that they are not registered; being past the rate limit is reported separately too, rather than being disguised as either.

  This is a deliberate trade and worth stating plainly: the endpoint can now be asked whether a given address has an account, which is what the previous behaviour existed to prevent, and what OWASP's guidance on this screen recommends against. The rate limit is the only thing holding that back — ten requests per origin per fifteen minutes, checked before the lookup runs rather than after, so a prober is throttled on the question itself. That is enough to make walking a mailbox list tedious, not enough to make it impossible.

- The top bar's navigation links lose their boxes. Each one was a pill that filled grey on hover and sat in a brand tint when it was the page you were on, next to a SIGN IN that is plain text — three weights of button competing in a bar that only ever needed one. They are text now, muted until hovered and brand-coloured on the current page, matching SIGN IN. The current page is also set in a heavier weight and marked `aria-current="page"`, so the one thing the tinted pill was genuinely doing — saying where you are — is now said in a way that does not depend on telling two colours apart, and is said to screen readers for the first time. The focus ring keeps its rounded box; it is the only outline in the bar that was ever load-bearing.

- Both landing heroes drop the media card they sat beside. It was a gradient tile with a play badge stamped in the middle of it, and nothing behind that badge: no `<video>` is rendered anywhere in the app, and clicking it did nothing. On the signed-out landing page the tile was otherwise empty, so half the hero was a rectangle promising a video that does not exist. The attendee home page had put a featured-event chip inside the tile, which repeated the first card of the event grid immediately below it, so that went with the frame rather than being restyled. Both heroes are now a single measured column of heading, copy and call to action; the panel keeps its brand fill and rounded foot but trades the dot pattern for a soft light wash, and its horizontal padding drops to the page's own so the heading finally lines up with the section headings and cards beneath it. Nothing else in either hero changed — the same words, the same **Join Now**, the same event grid. The community hero is cut with that same rounded foot now rather than running square to the page edge, so all three heroes read as one shape wearing three fills; the radius is a `--radius-hero` token instead of a number repeated per file, which is what let the community page square off unnoticed in the first place. Its photograph, scrim, height and centred copy are untouched.

- The pending email-change copy distinguishes the link's lifetime from the resend cooldown. The section read "The link expires on its own" next to a 60-second resend countdown, which invited reading the cooldown as the link's lifetime; the banner now names the 24-hour lifetime set by `otp_expiry`, the countdown is labelled as the resend wait it actually is, and both numbers come from constants in one module so the copy can never drift from the config.

- Email changes now complete on the new address alone. The previous double-confirmation flow sent a link to both the old and new addresses, and the new-address link alone could not finish the change — clicking it took you to sign-in instead of an email-verified page. A single confirmation link (to the new address) now completes the change, and the old address receives a separate notice telling its owner to contact staff if the change was not theirs.

- Account settings is one form now, not five separate cards. Each card shipped its own Save button that wrote only its own slice, so the page read as a stack of unrelated pages and a session held several stale copies of the profile; it is a single connected form whose one **Save Changes** button at the foot writes only what actually changed — the PATCH carries just the dirty groups, so the profile, the email and the password update together without an untouched field blocking or clobbering another. The speaker block sits inside that same form rather than as a separate card, validation errors render red under the input they belong to and are tied to it with `aria-describedby`, and the photo controls moved onto the avatar itself. Uploading and deleting now happen from the avatar's menu — a new `DELETE` profile-image endpoint exists purely so the delete action can remove the stored photo alongside the row.

- An email change is now a first-class pending state instead of a one-shot banner. Asking to change the address repaints the section as **Email change pending**: a header, the honest note that the confirmation link expires on its own, **Send it again** on the same 60-second cooldown, and **Cancel**, which voids the change server-side — the already-mailed confirmation link expires at once and a reload finds nothing pending — instead of merely closing the panel back to the field. The idle field pre-fills with the address on the account instead of a placeholder, and an emailed address that was re-requested within the cooldown is refused either way: the 60-second window now lives in a server route that reads the pending change directly, so a reload or a second tab can no longer re-fire sends into the old two-per-hour budget. That budget is raised to a number an account can actually use, and the double-confirmation mail both legs receive now differs by which address gets it — the target gets a plain confirm message, the address on the account gets an unmistakable "if this wasn't you, someone is trying to take over this account" warning, and both keep their confirmation link.

- Auth errors from the provider are no longer shown raw. supabase-js folds a response body that is `{}` into the literal `"{}"`, so a rate-limited or otherwise empty-failing reply rendered in the sign-in and sign-up forms as `{ }`; those two surfaces now map a 429 to "Too many attempts" and fall back gracefully on anything unparseable, while real provider copy ("Email already in use", a password rule) still passes through.

- Every "back" control in the app is now one component, and every one of them is a link. Nine pages had each hand-rolled their own — the event detail and register pages, both course pages, the event form, the staff and speaker event pages, the survey preview and account settings — and they had drifted apart in more than looks. Five of them were buttons wired to `router.push`, so they could not be middle-clicked, opened in a new tab, previewed on hover, or announced as anything more specific than a control that does something; they are anchors now. Two were painted with `text-muted-foreground`, which is not a token in this theme, so Tailwind emitted nothing for them and they took whatever colour surrounded them. All nine read the arrow glyph aloud to a screen reader, because a Material Symbols ligature is literally the text `arrow_back` unless it is hidden. Icon size, gap and colour now come from one place; only the spacing around the control is still the caller's to choose. Account settings loses its odd brand-coloured variant and its bare "Back", which now says where it goes.

- A detail page's back link now returns the reader to the page they came from. It always read "Back to Events", which was a guess: readers arrive from the landing page, the home feed, their tickets and now the community archive, and none of those is the events list. The origin rides along as a key rather than a path, so a hand-edited query string can only ever resolve to a route this app owns, and so the label travels with it — a bare path could not supply one. A link shared or bookmarked without the key still falls back to the events list.

- The event detail page has been widened, and its hero made taller on larger screens. The content column was capped narrow enough that the schedule and the sticky right column both ran cramped on an ordinary laptop. The staff view of an event moves with it, because a non-attendee opening the public page is redirected there and the journey should not change shape halfway through. The hero grows only from `lg` up: stacked on a phone its cover panel is decoration sitting above the title, and more of it would push the title off the screen.

- The audit log drawer stops dumping an entry's raw metadata as JSON. The metadata record carries per-action internals — check-in payloads, ticket references and the like — that no admin-facing page has a use for, so the drawer now shows only the action, actor, entity and timestamp instead of a `<pre>` block of internal state.
- Survey sends are now visible the moment an event opts in, and per-attendee sends no longer wait for a bulk send. The bulk action on the Surveys tab is renamed "Send bulk survey": it renders as soon as surveys are enabled, disabled and reading "Locked until event ends" until the event finishes — previously it was hidden entirely before the end, so an opted-in event that had not ended gave no hint the feature existed. The attendee drawer offers its per-attendee survey send while an event is opted in at all, locked until the event ends, and a single attendee can be surveyed the moment a finished event has never been bulk-sent: the individual send creates the survey row itself and opens the 14-day response window at that send, instead of refusing because no bulk survey existed. The attendees table now carries the event's survey status — off / locked / window open / window closed — under "Registered users", so every denied state says why, replacing the single "unavailable" banner.

- All six staff tables now render from one shared design instead of six hand-rolled variations. The events list, the attendee management drawer, the kiosk attendees panel, the organization roster, the audit logs and the email logs all compose the same table, toolbar, filter and pagination primitives, so columns, empty states and page math behave the same everywhere and a fix lands once instead of six times. Every table searches server-side too — events by title or venue, audit logs by action/entity/actor, email logs by recipient — each debounced so a query fires one request per settled pause rather than one per keystroke, and the filters (category on audit logs, role on the roster, type and status on email logs) read the same on every page. Row-level actions have left the table body: clicking a row opens a drawer holding the entry's details and, where it has them, its actions — Open/Kiosk/Edit for events, Check in / Send survey / Resend ticket / Cancel for attendees, Remove for members — instead of a column of buttons squeezed into the row. The organization roster now paginates at ten members a page instead of dumping the first fifty, and the standalone Courses audit page is gone: a course belongs to its event 1:1 and was already reached from the event's Course tab, so the orphaned all-courses list and its list endpoint are removed rather than left reachable only by URL.

- Staff tables keep their column headers through every search, filter and empty result. Each of them wrapped the table in a `loading ? spinner : empty ? box : table` ternary, so a search settling, a filter change, a page turn or a realtime check-in unmounted the whole table and its headers behind a spinner, and an empty match — including the audit logs' client-side category filter landing on a category with no rows — replaced the headers with a bare empty box. The events list, the attendee drawer, the kiosk attendees panel, the organization roster, the audit logs and the email logs now all render the table unconditionally and move the loading and empty states inside the body, beneath the headers: a refetch dims the stale rows (with `aria-busy`) while it fetches, and an empty result draws a single row under the headers instead of wiping them. Columns hold fixed widths so a search cannot reshape the grid, and long names, emails and details ellipsise instead of pushing their column wider. A failed refetch now keeps the last loaded rows on screen and says so inline — "Failed to refresh … — showing last loaded results." — rather than silently presenting an empty table as if nothing matched; that was already true of the attendee drawer and is now true of the audit logs too, whose data hook used to clear its rows on any failure.

- Q/A now lives with the course it belongs to instead of sharing the support chat module. The two features only meet in the `CHAT_MESSAGE` table: Q/A owns its own `QA_MESSAGE` rows, hangs off a course as `module_type='qa'` modules, and is read under the event's team rules, so the code that talks to it now sits in `src/modules/courses/qa/`, a submodule of courses, while the chat module keeps only support-chat code. The Q/A panel subscribes to its own realtime channel — `qa-module-<id>`, scoped to the module's row-level security — instead of the generic chat subscription, and the new replay-safe migration `00003` re-asserts the `SELECT` grant and `supabase_realtime` publication membership the browser needs for that channel on environments that drifted. The `/api/qa/*` routes are unchanged and stay under `src/app/api` (Next.js requires handlers there); they are now thin handlers over the submodule's service, and the two dead 410 stubs left over from the pre-extraction `/api/qa/[eventId]` shape are gone. How a course session behaves is unchanged.

- Confirming an email change now lands on the app's "Email verified" page, and the address shown in settings follows. The confirmation link GoTrue mails had no return destination wired up, so after the token was consumed the browser was sent to the bare site URL and the code that catches the app's row up never ran: the identity had moved, but the settings page still showed the old address. The route that sends the change now points the confirmation back through the app's callback, which exchanges the link and mirrors the confirmed address onto the account row before showing the "Email verified" page; the takeover warning on the old-address leg and the plain confirm copy on the new one are unchanged.

- Requesting a password reset now tells you what actually happened. The button used to answer "check your inbox" whatever followed — an unconfigured or unavailable mailbox reported "sent" and no mail ever left the server, because delivery ran after the reply with no way for the page to learn the result. The request now waits on the send, and when it fails the form says the email could not be sent instead of promising one that will never arrive. In development, the project's transactional mail — this link among it — is delivered into the local capture box when the seam is pointed at it, and when there is no capture box at all the success screen hands the reset link over directly so the flow still completes.

- Speaker and staff responses in an event's Q&A now carry their own highlight, so an answer reads as an answer next to the questions around it. Every bubble wore the same grey card before — a question, the speaker's reply, a facilitator's addition — and a reader could not tell who had written what until they read the name above it. A speaker's message now sits in a warning-tinted card under a Speaker chip, and a facilitator's, admin's or super admin's sits in an info-tinted card under the same Staff chip the support chat already uses; attendee questions keep the neutral card. The two labels are one classification helper, and its staff branch is the same floor the support panels use, so the chips cannot drift into disagreeing about who counts as staff.

- Deleting a question or a support message now removes it outright, and everyone watching sees it leave the instant it is deleted, instead of the message lingering on screen until a reload. Deletion used to be a soft delete — the row was kept, its `deleted_at` filed by an update and filtered out only in list reads — so the chat and Q&A panels went on showing a deleted message until the page refetched. A delete is now a real `DELETE`: the row is gone from the database with no tombstone kept, and because the chat tables log their full rows so the realtime channel can route them, every open panel drops a message the moment it is deleted. Updates still land the same way — the difference is that deleting something removes it rather than hiding it.

- Deleting a question now says it is happening on the message itself. A delete used to fire a silent request and the bubble kept its full strength until the realtime event removed it, so a Q&A moderator could not tell a delete that was on its way from a delete that had quietly failed. Clicking delete now dims the bubble immediately and swaps its control for a small spinner and "Deleting...", held until the row actually leaves; a delete that is refused — or that never reaches the server — restores the bubble, re-enables the button, and shows "Deleting failed" beside it before clearing on its own.

### Added

- Event memories now carry the photographs taken at the event. A finished event holds its own archive: staff upload the pictures under a new **Photos** tab on the event, the cards on `/community` lead with a mosaic of them, and following one opens `/events/{id}/memories` — a page of the photographs, with a full-screen viewer that pages on the arrow keys. The strip used to be a row of text cards that restated the detail page they linked to — the card said so in its own note, because an event held exactly one cover image and nothing behind it.

  The archive is its own route rather than a section of the event page, because the event page is a page about an event that has not happened yet: a register card, a schedule, a map. Following "view 12 photos" and landing on a registration form for a session that already finished is the redundancy the strip was supposed to stop being. The event page instead carries a four-tile strip through to the archive, so the pictures live in one place and are pointed at from the other.

  A memory card answers a hover the way an event card does — the same lift, shadow and 300ms easing, and the same scale on the pictures inside it. The two sit in grids of the same shape on pages a reader moves between, and a card that responds differently to the same gesture reads as a different kind of thing. The movement is behind `prefers-reduced-motion`: a reader whose system asks for less of it gets the shadow and none of the scaling, on the card and on the pictures inside it. Both now build on one shell rather than two copies of it, which had converged to within a single class; what goes inside stays each card's own, since a cover with a status badge and a mosaic of photographs have nothing to share below the frame.

  A memory card carries no venue. An address is live-event information — a memory is looked at, not travelled to — and the event's own page still holds it for anyone who wants it.

  An event nobody photographed keeps its card, holds the same picture area every other card has, and opens the same archive page — empty, and saying so. An empty archive is an answer; quietly diverting to the event page instead is the redirect this whole change exists to remove, and a card with its picture area dropped is the text-only strip it replaced.

  Photos are a facilitator's write, not an admin's, and they are the only such write on an event. The person holding the pictures is the one who was in the room, and routing them through an admin is how an archive never gets posted — so the capability sits beside the meeting link, scoped to the event that facilitator is assigned to and no other. It touches `EVENT_PHOTO` and never the event row, so nothing else about an event became editable.

  The objects live under `events/{id}/photos/` in the bucket the cover already uses, which is what makes a published event's photos public without a second visibility rule to keep in step with the first: the storage route resolves access from that prefix, and the table's row policy delegates to the event's own. A draft's photos answer 404 — the same refusal a missing event gets, so a photo count cannot be used to learn that an unannounced event exists.

  The strip resolves in two queries no matter how many cards it shows, rather than one per card, and it is its own endpoint rather than a flag on the events listing — the archive is the expensive half, and the staff table, the public list and the landing page would all have paid for it to feed one strip.

- A course can now hold part of itself back until the event is over. Staff tick, under the event's **Course** tab, which of its own modules are released afterwards; those modules stay out of the room during the session and open to everyone who held a ticket the moment the event ends. They appear under **My Courses**, which is new — once an event is over its page is the last thing anyone revisits and its room shows a session that has ended, so without a listing the material would sit behind a door nobody has a reason to open.

  The unit is the module, not the course, because an event owns exactly one course — `COURSE.event_id` is UNIQUE, and has been since the first migration. Both kinds of material therefore live in one curriculum: the modules worked through in the session, and the ones kept for afterwards. Only that event's own modules can be chosen, and only its own ending releases them. Q&A modules are not offered: one holds no material, and its read policy wants a live session behind it, so releasing one would leave a panel that never delivers.

  Nothing runs to release them. There is no job, no scheduled task and no row written anywhere: the release is recomputed from the clock on each request, the same way `effectiveEventStatus` has always turned a finished event into a completed one without touching it. A module held back by an event ending at 17:00 is hidden at 16:59 and readable at 17:01, and an edit to the list takes effect at once because there is no derived copy of it to fall out of step. The list lives in `SYSTEM_SETTING`, a jsonb table that has been in the schema since the beginning with no reader until now — so the whole feature lands without a migration.

  Held-back modules are stripped from the feed rather than hidden by a component, because material a component hides is still on the wire, and the room is the surface people already have open when a session ends. Staff and the event's assigned speakers see the whole curriculum throughout, since they are the ones assembling it. Every surface that serves course content — the room feed, the by-event fetch and the storage route that hands over the PDFs and videos — now asks one gate rather than three near-copies of the same rule, which is what keeps released material downloadable instead of a curriculum of dead links.

- **Timezone.** Event dates and times are now read in one named zone (`NEXT_PUBLIC_APP_TIMEZONE`, defaulting to where the events are run) rather than in whatever zone the code happens to be executing in. `EVENT` stores a bare date and two times with no offset, so "17:00" only means something once a zone is named — and the two halves of the app were naming different ones. The browser used the viewer's; Workers has no local zone at all and used UTC. An event ending at 17:00 local was therefore still _running_ as far as the server was concerned until 01:00 the next morning, while the page in front of the attendee had already called it finished.

  This was live before this release, in the "Completed" badge, the archive/upcoming split, the meeting-link release and the room's own opening gate — the release above simply made it impossible to leave alone, since "opens when the event ends" is the one place a reader watches the clock. Verified inside workerd rather than assumed: a bare parse there really does answer UTC, and the zone-aware one answers correctly, including across a daylight-saving boundary.

- The events page has a search box, for attendees and signed-out visitors alike. It searches titles and venues server-side — the same query staff have always had, which the shared hook already exposed and this page simply never rendered — and it composes with the Upcoming/Completed tabs rather than replacing them: the tab counts report what the term matched, so searching for something filed under the other tab tells you where it went instead of leaving you on an empty list wondering. The empty state names both, as in "No completed events match “summit”."

  Two things had to be fixed for it to work at all. The page swapped its entire self for the loading skeleton on every fetch, which with a search box on it would have unmounted the input during the pause after each keystroke and taken the cursor with it; the heading, tabs and search now sit outside every loading and error branch, and the skeleton draws only the card grid instead of a second copy of the page's chrome. And the tabs were styled with `text-foreground`, `text-muted-foreground` and `bg-surface-hover`, none of which is a token in this theme — Tailwind emitted no rule for any of them, so the selected tab and the unselected one rendered the same colour on the same transparent background, separated only by font weight. They use real tokens now, and carry `role="tab"` with `aria-selected` so the selection is not left to colour at all.

- The speaker's engagements page splits into Upcoming, Finished and Drafts tabs, with a headline card for the engagement that matters right now. A past event kept its **Upcoming** badge and sat in the default list because the reading code served the stored `status` column, which the publish flow never advances; the read paths now compensate for the time window, so a finished session stops being "upcoming" and moves to its own tab. The status split is server-side — the speaker's own endpoint filters by the same buckets, so the client never holds the unfiltered mix and each tab is fetched at most once per visit.

- The headline card picks the live engagement, or failing that the nearest one still to come, from the always-loaded upcoming view, so it stays put while the tabs underneath swap. It reuses the shared status badge, timer and date formatters rather than inventing a second reading of when an event starts, and says which engagement it is about with a _Happening now_ or _Up next_ eyebrow. Each tab has its own empty state, and a failed load keeps the last rows on screen with an in-place warning instead of blanking the page.

- An online event now carries its joining link, and withholds it until the event starts. `meeting_url` is nullable and nullable on purpose: the room usually does not exist when the event is scheduled — somebody creates the event in March and makes the Meet link on the morning. A `NOT NULL` would have forced a placeholder to be invented at creation, and a placeholder link is worse than none, being indistinguishable from a real one to the person clicking it.

  Who may hold it is the whole design. A meeting link is an unauthenticated door: anyone with it walks in, which makes both the capacity cap and the payment decorative. So it is served to staff, who have to set it, and to a ticket holder only once the event has started — the same edge the register card already unlocks **Enter Room** on, so an attendee meets one rule rather than two. Everyone else is served `meeting_url: null`, withheld in the API rather than hidden in the page, because the JSON is what is actually served. The key stays present when withheld, so the shape of a response cannot be used to work out whether a link exists. The event listing strips it from every row unconditionally — it selects `*` and feeds the public list and the landing page, and no listing surface renders a link.

  An attendee sees a card in place of the map: before the event, that the link will appear there when it starts; after, the link itself, opened with `noopener noreferrer` so the destination is not handed the page it came from. "Not posted yet" and "you may not see it yet" read identically, deliberately.

  Staff set it from a panel on the event's Overview tab, and only from there once the event exists — the field appears on the creation form because a row that does not exist yet has nowhere to hang a panel, exactly as the cover image and the team roster already work. Saving the Details tab does not send the column at all, so an admin editing the price cannot silently revert a link a facilitator posted minutes earlier. The panel sits behind its own endpoint and its own capability rather than the edit form. Editing an event is admin-only by design — "facilitators are foot soldiers who run kiosk check-in but never touch event details" — and the link is made on the day by whoever is running the session. `meeting_link` is the one event column an assigned facilitator may write, scoped to their own events; widening `edit` instead would have handed them the price and the date with it. The URL is parsed and pinned to http(s), since it is rendered as an `href` and `javascript:` in an href is script execution on click, and it is kept out of the audit metadata, which every admin can read.

- An event is now onsite or online, as a column rather than as a hint. The only thing that could say an event was online was prose somebody typed into the venue — "Zoom", "online via Meet" — which meant nothing in the app could act on it. The map card mapped that text and produced a confident map of an office in California; the hero labelled it **Venue**; the calendar invite carried it as a street `LOCATION`. Every one of those read the venue and had no way to tell a hall from a meeting link.

  `event_type` is an `event_mode` enum of `onsite` and `online`, and every event that already exists is onsite — the honest default, since nothing in the stored data distinguishes the ones that were really online. Picking Online on the event form locks the venue address and drops it, renames the Venue field to **Platform**, hides the map on the event page, and labels the hero fact **Online**. Switching back to Onsite hands the address back, because it was disabled rather than discarded.

  `venue_name` stays required and simply widens its meaning to "where it happens": a hall when onsite, a platform when online. Making it nullable was the alternative, and it would have weakened a constraint a dozen readers depend on — the hero, the ticket card, the ticket email, the calendar links, the landing page, the speaker views — to buy nothing any of them needed.

  Dropping the address is enforced three deep, for the reason a disabled input is not a rule: the form sends null whatever the box still holds, the API refuses the pair as a 400 rather than letting a constraint answer 500, and `chk_event_online_has_no_address` makes it true against a direct write. A patch that names only one half of the pair is checked against the stored row, the same way a patch that moves one end of the time range already was.

- An event can now carry a capacity. There was no way to say how many people a session seats — not on the create form, not on the event, not in the database — so a venue with forty chairs sold tickets until somebody noticed and unpublished the event by hand. Capacity sits with the rest of the event basics on both the create form and the event's Details tab, and is optional: leaving it empty means uncapped, which is what every event that already exists is, so nothing scheduled today changes.

  A seat is a ticket that has not been cancelled — the same thing the staff Attendees column has always counted — so a cancellation returns the seat to the pool without a second number to keep in step. A capped event shows what is left of it on the register card, and once the last seat goes the register button locks and reads **Sold out**; the staff list reads `12 / 50` instead of `12`. Attendee counts stay staff-only: a reader is told how many seats remain, never how many are taken.

  The registration route refuses a sold-out event before a checkout is opened, and so does the checkout itself, because that is the last refusal that is still free for the buyer. Neither is the rule. Two people checking out at once both read the same count and both pass, so the cap is enforced in the database, on the ticket insert, behind a lock on the event row — the app's checks are there to say so in words before any money moves.

- An event's cover image can now be set while the event is being created, instead of only afterwards. The Create Event page carries the same cover section the event's own Details tab does — one definition of the heading, the copy under it and the control, so the two cannot drift — and the page now reads in that tab's order throughout: cover, event basics, pricing, team. A preview of the chosen image stands in for the uploaded one, and a file the bucket would refuse is reported at the moment it is picked, not after an event has been created around it. The image is held in the browser and uploaded once the event exists, because a cover is stored at `events/<id>/cover.<ext>` and there is no id to store it under until the row has been written. If that upload fails the event has already been created, so the message says exactly that and the form does not offer to submit itself again — you land on the new event, where the cover can be re-picked under Details.

- A ticket can now be opened as a boarding pass on its own page. Buying a ticket gave you a card in the tickets list, and nothing else: at the door you scrolled the list to find it, and there was no URL to hand to a scanning staff member or to hold side by side with the kiosk. `/tickets/<ticketId>` renders the same phone-scale QR and code as the email, the event's details, and the ticket's own status — a **Registered** banner that flips to **Checked in** with the time the moment a staff member checks it in at the kiosk, because the page subscribes to the same realtime the kiosk's attendee table uses. Only the ticket's owner or an event staff member can read it; anyone else's URL answers "Ticket not found" rather than leaking that the ticket exists.

- The QR check-in code is now short enough to type. It was a long random string that filled the ticket card and, whatever a phone displayed, could not be handled by a gate that only had a keyboard — the convenience a QR existing at all is for. Tickets now carry a six-character lowercase hex code, `a1b2c3`, short enough to read aloud at the door and to type into the kiosk, whose lookup strips whitespace and lowercases what was typed so the code is accepted the way humans say it. Short codes collide, which is precisely why the code used to be long: the database's unique constraint on the column is gone, and issuance now allocates a code it actually owns before the ticket exists — retrying until it finds one no live ticket holds — and a code a ticket has given up (checked in or cancelled) is returned to the pool, because the allocation only looks at tickets that still expect a check-in. ### Fixed

- Deleting an event now takes its images with it. The sweep that clears the bucket was gated on the event having a cover, which read as "does this event have images" — untrue the moment an event could be photographed without ever being given one, and the whole folder was then left behind. It also listed the event's folder without recursing into it, because `storage.list()` does not: asked for `events/{id}` it reports `photos` as a single directory entry, which the collector turned into a key that deletes nothing and then never looked inside. The keys now come from the table that records them, with the folder still listed alongside so an object whose row never landed is collected too.

- The event hero opens its cover picture. Clicking the picture on an event page — staff or public — shows it full size on a dimmed backdrop, closed by clicking away or pressing Escape. The affordance is the cursor and nothing else: no lift, no zoom, no dimming under the pointer, because at that size anything that moves or recolours reads as the page glitching rather than as an invitation. It is a real button rather than a div with a handler, so the cover opens from the keyboard too, and the status badge in the corner is transparent to the pointer so it cannot cut a dead patch out of a panel that is otherwise clickable end to end. An event with no cover stays inert — enlarging the placeholder gradient would show the reader nothing they cannot already see.

  The overlay carries no close button. The shared one is a ghost control drawn in the foreground colour, which is legible over a pale cover and invisible over a dark one; legibility that depends on which image somebody uploaded is not legibility.

- The Manage Course page sits in the same column as every other staff page. It measured its own — `px-16 pt-24` and no maximum width at all — so on a wide display the curriculum stretched the full viewport while the event page it is reached from stopped at 1360px, and stepping between the two moved every control on screen. It now renders inside `StaffPage` with the shared header, and the test helper three other suites already use holds it there.

- Errors from the API all arrive in one shape. Twelve refusals across the event, organization, community and module routes wrapped their message as `{ error: { message } }` while every other route sent `{ error: "..." }`, and the split had already cost three clients a normalizer apiece to paper over — the module editor's existed because reading only the nested form turned a 409 into a generic failure, which told the author nothing about what to do next. The staff organization page, the event edit form, the team panel, the survey panel and the meeting-link panel each read the message back through one of those; they now read it directly. The one exception is the email-change route, which nests under `ok: false` to carry a `retryAfter` and a provider `code` that a string cannot.

- A request that fails validation comes back with a message rather than an object. The twenty-three routes that validate a body each answered a failed parse with `parsed.error.flatten()`, which put Zod's `{ formErrors, fieldErrors }` under `error` — the key every other route answers with a string. Clients read that key straight into state typed `string | null`, and because `res.json()` is `any` neither TypeScript nor a test saw the mismatch: the registration form and the Q&A panel would each have put an object where a message belonged, which React refuses to render. So a 400 that was meant to explain itself took the surface down instead. One helper renders these now, and it keeps the field paths that `flatten()` was there for — `capacity: Invalid input: expected number, received string` — rather than dropping to a bare "Invalid request". `flatten()` is deprecated in Zod 4 as well, so all twenty-three sites were going to have to move regardless.

- The live-highlight route refuses an unauthenticated caller in the same words as every other API route. Its two 401s answered `{ error: "Unauthorized" }` where the other thirty-eight answer `{ error: "Unauthenticated" }` — the word `guardFailure` renders, and the one the account-settings client's comment names as the auth-route convention. Nothing was broken by it, since that client folds any string error into its message, but the API layer had two words for one condition and nothing on screen said which a given route would pick. The middleware answers in that word too, rather than keeping "Unauthorized" for refusals of its own: it and the route's own check answer the same condition, and which of the two catches a request first is an implementation detail a client cannot see — so a client detecting "needs to log in" had to know both spellings. This route writes the literal by hand rather than going through `guardFailure` because its gate is resource-scoped rather than a role floor, and forty hand-written copies of one response body are forty chances to pick the wrong word, which is why a test now scans for the second word instead of trusting the copies.

- A route that has nothing to return says so in one shape: `{ ok: true }`. Sixteen routes acknowledged a write, eight of them with `{ success: true }` and eight with `{ ok: true }`, and from outside there was no way to tell which spelling a given route would pick — the account-settings client is the only reader of either, and it reads `ok`. Three of those bodies were not written by the route at all: `deleteEvent`, `publishEvent` and `deleteCommunityLink` each returned a `{ success: true }` of their own that the route serialized straight to the browser, which is how a module's return type came to define an HTTP payload. Those functions throw when they fail, so the constant told the caller nothing it did not already know by not being thrown at; they return nothing now, and the routes write the wire shape themselves. A scan holds the single spelling in place, alongside the ones already guarding the error shapes.

- The tests that hold the API's error shapes in place now watch the helpers as well as the routes. They scanned `src/app/api` only, so the responses routes build for themselves were covered while the ones they hand back from `guardFailure`, `badRequest` and the `course-access` guards — the files where this shape drifted both previous times — were not: today's helpers are correct, and nothing would have failed if tomorrow's were not. The scanned set is now discovered by the response a file constructs rather than by where it sits, so a helper added next week is covered without anyone remembering to add it, and it is named once instead of being redefined in each of the three sweeps. Comments are stripped before matching, since these files document the shapes they no longer render.

- A lesson highlight set in the course room now reaches the other viewers on the spot. The realtime path streamed the UPDATE event but the row never carried its changes: `LIVE_SESSION_STATE` still decoded with the default replica identity, which emits only the primary key on an update, so the event arrived at every room other than the speaker's with no lesson id in it — each client cleared the highlight the moment it was set, and only a refresh (which re-seeds from the API) brought it back. The table is now `REPLICA IDENTITY FULL` (00016), matching what 00013 did for the realtime message tables, and the full updated row rides the event.

- Live-highlight changes in the course room now arrive as they happen instead of up to five seconds late. The room polled its own highlight endpoint every five seconds, so a speaker's click surfaced with a delay long enough to feel like the toggle had missed, and every room open on the event paid that poll for as long as it sat there. The highlighted lesson now streams to browsers over Supabase realtime from the same shared subscription seam the app's other live surfaces use, with one fetch on room load seeding the current value — the room shows the marker the moment the speaker sets it, and clears it the moment they drop it.

- The course-room clock no longer redraws the whole room every second. The old countdown lived in the room-access hook as a one-second interval's worth of state, so each tick re-rendered every card beneath it — the profiler showed the timer and its dependants as the room's biggest consumers, a session hero, a current-topic card and a list of lessons rebuilding sixty times a minute on a page that was otherwise still. The ticking now sits in the navbar leaf and redraws only its own elapsed and remaining numbers, while the room-level edge states (started, ended, live module) flip on a coarse 30-second heartbeat matching the hero's existing clock. A start or end is noticed within half a minute instead of within a second, and nothing else on the page re-renders in between.

- The course-room navbar clock runs forever past the event's end. The elapsed counter measured `now − start` with no upper bound, and the session bar only knew whether the event had started, so a finished event kept counting what should have been over — the Remaining column had long since sat at `00:00:00`, while Elapsed kept climbing and the bar looked every bit as live as a room mid-module.

  The counter now clamps at the event's `end_time`: elapsed freezes at the session's full length, remaining at `00:00:00`, and the one-second clock stops picking itself back up once the end passes — there is nothing left for it to compute. The navbar also knows the end edge rather than only the start one, so in place of the two columns it shows a static **Ended** label, matching the badge the hero already carries for the same moment. It stopped telling you the event was still going, because that was the one statement the old timer was actively making wrong.

- The staff survey opt-in is a labelled row now, not a bare pill in the card header. The old pill read as disabled when off and turned into a solid blue blob when on, so staff could not tell the survey state at a glance. The switch now sits beside its "Opt-in to post-event survey" label with a visible On/Off word, so the state is readable in both colours and the dimmed-grey "off" styling no longer pretends the control is disabled.

- The staff survey opt-in keeps its state when an admin leaves the Surveys tab and comes back. Toggling the switch saved to the server but only into a local copy, and the page mounts the panel per tab — so leaving the tab unmounted it and returning rebuilt it from the stale event, making the switch read as if the toggle had never happened until a full refresh. The panel now folds the saved value back into the page's event, the same way the meeting link, cover upload and edit form already did.

- Colours that were never being applied are applied now. Sixty-two class names across eighteen files named tokens this theme does not define — `text-foreground`, `text-muted-foreground`, `text-destructive`, `bg-surface-hover`, `bg-primary`, `text-primary-foreground`, `bg-background`, `to-background`, `text-accent`, `border-border-strong` — leftovers from a different palette's naming. Tailwind emits nothing for a class it cannot resolve, and nothing is not an error: the markup looked right, the build passed, and the element simply inherited whatever surrounded it.

  Some of it was cosmetic drift, but not all. Error text on eleven surfaces was rendering in the ordinary foreground colour rather than red, which is the one message on a page that must not read as body copy. The **Pay** and **Register** buttons on checkout and event registration had no background at all — a primary call to action wearing dark text on the page's own background. Muted captions sat at full contrast, so the hierarchy between a label and its value was invisible. And selected tabs on the staff event page were separated from unselected ones by font weight alone.

  Each name now points at the token that was meant: `text-fg`, `text-muted-fg`, `text-error`, `bg-muted`, `bg-brand`, `text-brand-fg`, `bg-bg`, `to-bg`, `text-brand`, `border-border`.

- An online event's card no longer claims to be somewhere. Every event card drew the same map pin beside its venue line, whatever the event's mode, so an online session showed a location marker next to the name of a platform — "📍 Zoom". The card now takes the camera icon for an online event and the pin for an onsite one, the pairing the event detail page and the mode picker in the create form already used.

  The reason it was wrong is that the pairing existed in three places and the card was not one of them: each surface that needed it had spelled it out inline, so a fourth surface simply picked whichever icon its author typed. It is one function now, and the card, the detail hero and the form read from it. Rows written before the mode column existed read as onsite, matching the default the column itself carries.

  The same fix reached the speaker's Upcoming Engagements list by way of a related problem: `/api/speakers/me/events` had its own hand-copied version of the converter every other producer of that shape goes through, and it had been quietly falling behind — it still flattened a `COURSE` embed its consumer had stopped expecting, and it dropped each new column as the shape gained one. It now goes through the shared converter, which also means those cards show their cover images rather than always falling back to the gradient.

  While the icon was the only thing saying where an event happens, it was also the only thing saying it to a screen reader — and Material Symbols renders through ligature text, so the venue line announced itself as "videocam Zoom". The icon is hidden from assistive technology now and the line carries a real label.

- Requesting an email change is rate limited for real now. What stood in for one was a 60-second cooldown that fired only when the address being asked for was the one already pending, and that measured `email_change_sent_at` — the column `cancel_pending_email_change` sets to NULL. So either naming a different address each time or pressing Cancel between attempts walked straight past it, both from the settings form, no tooling required. That matters more than a stray extra email: auth mail is metered per project, not per account, so anyone signed in could exhaust the hourly budget and leave every other user's signup confirmation and password reset undeliverable — which is exactly how a brand-new account ends up being told it has sent too many emails.

  A limiter cannot key on state the limited party can clear, nor on the value they are asking about. Attempts are now counted per caller and per origin in a table of the app's own (`EMAIL_CHANGE_ATTEMPT`), on the pattern password reset has always used, and neither trick moves the count. The per-origin allowance is deliberately loose, because a venue's wifi can put a whole audience behind one address.

  The 60-second cooldown stays where it was, doing the job it is actually good at: absorbing a double-click without spending a database write. It just is not the only thing standing between one user and the whole project's mail.

- An email change that was rate-limited now clears once the minute is up. The resend cooldown measured its elapsed seconds from `email_change_sent_at`, which GoTrue does not always return — and a missing one was read as zero seconds ago, so the window never opened. Every retry of that address answered "Too many attempts" for as long as the change stayed pending, and since only cancelling clears the pending record, waiting could not fix it however long you waited. A send time the server does not have cannot show the window is still open, so it no longer blocks on one.

  The settings page was reading the same field the same wrong way, so half the fix did not show: on every mount it restored a pending change with the full 60 seconds still to run, and a reload always beat the countdown it had just started. Both now read the remaining wait through one function rather than deriving it twice, which is what let the two drift apart in the first place.

- A refused resend now says how long is left — "Try again in 41 seconds" — instead of "Please wait, then try again", and the resend button counts that same number down rather than offering a press already known to fail.

  Most of those refusals come from GoTrue rather than from our own cooldown, and GoTrue states the wait in prose ("For security purposes, you can only request this after 41 seconds") because there is no `Retry-After` on the response and no field for it on the error. The 429 branch answered before it ever read the message, so that sentence — the only copy of the number that reaches us — was discarded, and a refusal with a perfectly knowable countdown arrived as an open-ended one.

  Where no number exists the message now at least says which limit was hit. That case is the project's hourly send budget — `email_sent`, which is counted per project rather than per user — so it refuses accounts that have sent nothing at all, a fresh signup included. Reporting it as "please wait" read as a short personal cooldown, and left anyone who waited the usual minute looking at an unchanged message with no idea the limit was not theirs. It now says the limit is the app's and is shared. A refusal from GoTrue is also logged with its code and wording, since the budget itself is set in the Supabase dashboard and nothing in the repo records what it is.

- The email section no longer points at a field it has removed. While a change is pending, the section replaces the address input with the "Email change pending" box — but its copy still read "to send to a new address, type it below", and there was nothing below to type into. The likely reading of that is that the page is broken, when the way to a different address is the Cancel link sitting right there, which the copy never mentioned. It now says so. Reachable on reload rather than only just after sending, since the pending record is read back from the auth server on mount.

The reference is now cleared in the same request that unassigns them.
- Reordering course modules and lessons no longer relies on drag and drop. Dragging was unavailable to keyboard and touch users, and the drag affordances were easy to trigger by accident while scrolling. Modules and lessons now move with explicit up/down buttons: a module's buttons reorder it among the others, and a lesson's buttons reorder it within its module or, at either end of the module, across into the neighbouring content module — lessons never land in a Q&A module, which has no content of its own. The cross-module move is persisted in the same request, so a course reloads with the lesson in the module it was dropped next to.
- The Q&A module lock control has been removed from the course builder entirely. The lock's only purpose was guarding a staff-facing moderation flow that no longer exists in this interface, so the toggle and its badge no longer appear.
- A ticket email sent to an unresponsive mail server no longer leaks its connection. When the SMTP session timed out, the abandoned session was left parked waiting for a reply that never came, so the socket it held was never closed — and each retry opened another beside it, three per message against a stalled host. Those connections accumulated for the life of the isolate, and because a Workers isolate serves many requests over minutes or hours, a spell of trouble at the mail host degraded every later request that isolate happened to handle. Closing the connection is now the job of the code that opened it, which runs whether the session finishes, fails, or is abandoned to the timeout.
- Server-side database clients are no longer rebuilt for each request. Every one of them started a token-refresh timer that was never stopped, and that timer held the entire client — auth, realtime and query layers together — in memory permanently, so a long-lived isolate accrued one per request until it ran out of room. A single client is now shared across requests with the refresh timer off; it holds no per-user session, so there was never anything to keep apart.
- The course builder's move buttons now say where a lesson will land. Hovering an arrow highlights the exact spot — the row it swaps with inside a module, or a "drops in as the first/last lesson" handle on the neighbouring content module for a crossing move — and every button's accessible label names the destination. A moved lesson briefly glows, and a move across modules announces its new home and scrolls it into view, so a reorder registers even when the target is off-screen. The drop indicator is an overlay rather than a row in the document flow, so hovering an up-arrow no longer shifts the layout beneath the cursor and makes the preview blink between modules.
- The staff nav rail now animates open and closed instead of snapping. Its links toggled `justify-content`, which the browser cannot interpolate, so the icon teleported to the centre the instant the rail began to shrink, and the label's width jumped because `width: auto` is not a transitionable value either. Each icon now lives in a fixed-width box that never moves between the two states, and the label reveals by animating `max-width`, `margin-left` and `opacity` — closing glides and nothing cuts into place. Keyboard focus expands the rail and reveals the labels too.
- The staff nav rail no longer sticks open after you click a link. The clicked link keeps focus across navigation, and the rail expanded on `:focus-within` — which matches any focus, mouse clicks included — so it stayed wide until you clicked somewhere else to move focus. The rail now expands on hover or keyboard focus only (`:focus-visible`), so a mouse-clicked link closes it the moment the pointer leaves.
- Uploading a new profile photo now updates the photo in the account settings page immediately, without a refresh. The upload already wrote the new URL to the database, but only the navbar heard about it — it subscribed to a one-off `profile-photo-updated` event the upload fired — while the settings page read the stale URL from the in-memory session user, so its preview changed only after a reload. The session now accepts an update of its user, the upload writes the new photo URL into it, and every reader — the navbar and the settings page alike — sees it the instant the upload lands. The hand-rolled event is gone, so there is one source of truth for the profile photo instead of two.

### Security

- A lesson link is recognized as a YouTube video only when its host is one. The check asked whether the hostname _contained_ `youtube.com` or `youtu.be`, so `youtube.com.attacker.example` and `youtu.be.attacker.example` passed it, and a lesson pointing at an attacker's host was rendered as an embedded player instead of the labelled external link every other destination gets — hiding where the content actually came from. The hostname is now matched whole against the YouTube domains, and non-HTTP schemes are refused outright.

- A role allowlist no longer admits every signed-in account. The server had one variadic "minimum role" check, so a list like `attendee, facilitator` — meant to admit those two — silently admitted speakers and admins as well, and `facilitator, speaker` admitted every role above attendee. Ticket and payment reads even had to compensate by scoping themselves by entitlement inside the handler, because their guard let everyone through. Staff checks now use an explicit "at least this level" guard, and the few endpoints that genuinely want a specific set — editing a speaker profile — match the role exactly, so a higher role is refused instead of silently allowed.
- Records only their owner or the event's own team may touch can no longer be changed by any staff account. A facilitator or speaker could act on records they had no part in: any speaker could read any course's curriculum and delete any Q&A question, any facilitator could delete any support message, and any facilitator could delete any speaker profile. Those endpoints now check ownership or assignment first — a course or question is reachable only by its event's assigned team, a support message by a participant or the case's assigned facilitator, and a speaker profile by its owner or an admin. Speaker pages also require a sign-in now, and the staff courses page redirects to the access-denied screen instead of rendering a permanently blank page.
- Draft event covers are no longer readable by every signed-in user. Covers are served through `/api/storage/event_images/...`, whose object keys are `events/{id}/cover.png` against sequential ids, so any account could fetch the cover of an unpublished event by guessing the path. Serving one now requires the event to be published, or the facilitator role — the same rule the event listing already applied to drafts.
- Course material is no longer readable by any signed-in user. `/api/storage/[bucket]/[...path]` read any bucket and object key straight from the URL using the service client, bypassing row level security — paid course videos and assets were available to anyone with an account. Access now requires a live ticket to the event teaching the course, a speaker assignment to it, or the facilitator role.
- Storage requests are answered `Cache-Control: private`. Entitlement is per user, and the previous `public` response could be served from a shared cache to someone not entitled to it.
- Uploaded images no longer carry the uploader's location. A phone writes GPS coordinates, its serial and the exact time into every photo it takes, so a profile picture published the uploader's home address to anyone who downloaded the file. Metadata is now removed on the server, in the one place every upload passes through — the browser-side resize strips it too, but only for images it can decode, and a request sent straight to the endpoint never reaches the browser's copy at all. Pixels are untouched: the container's metadata segments are dropped without decoding or re-encoding, so quality and colour profile survive exactly. Which way up the photo goes is carried across on its own — a camera leaves a portrait photo's pixels sideways and records the rotation in the same block as the coordinates, so dropping the block wholesale would stand every portrait photo on its side. Only that one value is rebuilt, into a segment holding nothing else. Nothing new is refused — a file the stripper cannot read is stored as it arrived, since what may be uploaded is the route's judgement rather than the stripper's.
- Facilitators can no longer edit events they do not manage. The event write endpoints trusted the facilitator role alone, so any facilitator could edit or publish any event and read any event's attendee list, and delete — reachable by the event owner's own assistants — could destroy an event they merely helped run. These actions now require an admin or a facilitator assigned to that specific event, and delete is admin-only, the same rule the event rooms already enforced.

### Fixed

- Creating a course from the speaker or staff page works. The create form sent an empty description as `null`, but the API schema accepted only a string or an absent key, so every "Create Course" click was answered `400` and the curriculum builder never appeared. The schema now accepts `null` — the value the DAO already stores. Fixing that surfaced the next gate: the speaker check filtered an embedded table it never selected, which PostgREST answers `PGRST108`, so the query returned nothing and every assigned speaker was `403`ed. The check now resolves the speaker profile and looks the assignment up directly, like the speaker page already did. A failed create no longer fails silently either: the page shows the API error instead of doing nothing.
- Assigning speakers to an event actually saves them. The bulk-assign validation had the same broken embedded filter — it selected only profile ids while filtering on the user's role, so PostgREST answered `PGRST108` and every assignment was silently dropped when an event was created or edited.
- An invitation is no longer accepted by machines. `/invite` redirected straight into Supabase's verification endpoint, and verification spends the single-use token — so a mail scanner, security gateway or link previewer following the address in the message consumed the invitation before the invitee opened it, leaving them a dead link and an address that then counted as registered. Opening the page now does nothing: it offers an Accept button, and only that submission verifies — no scanner submits a form. Acceptance is also handled by the application rather than by a redirect to Supabase, so the token stays in a request body instead of travelling through a URL, and a refresh cannot resubmit it.

- An invitation nobody accepted can be sent again. The invite refused a second attempt for an address Supabase already held an account for, and it holds one from the moment the first invitation is issued — so a facilitator or speaker who never received the mail, or whose link was spent by a mail scanner before they clicked it, could not be invited again by any means. Whether the invitation was accepted is now decided by whether anyone ever signed in with it, and an unaccepted one is replaced by a fresh invitation, carrying whichever role was chosen this time. An address whose owner has signed in is still refused.

- Image uploads work again. Every upload route — event covers, profile photos and course material — failed on the deployed site, because the resizer compiled its WebAssembly while answering the request and the Workers runtime only permits that at startup. No cover image had ever uploaded successfully in production, and the build gave no warning. Images are now shrunk by the browser before they are sent, which removes the WebAssembly rather than working around it: the upload itself is faster, since the smaller file is what crosses the network, and photos taken in portrait are no longer stored on their side. Videos and documents are passed through untouched, and a browser that cannot read the image uploads it unchanged instead of refusing.

- Pages no longer fail outright in the minutes after a deploy. A freshly started isolate spends its CPU budget loading the application before any handler runs, so a page that fans out into many requests at once could exhaust it and return nothing — `/tickets` was the worst, issuing ten server requests for one navigation, and even `/favicon.ico` failed because the project had no icon and each request booted the server to render a 404. The ticket list now arrives complete in a single request and each ticket's QR is drawn by the browser from data it already holds, cover images on `/` and `/events` no longer look up who is asking before serving a published one, and an icon exists. Warm isolates were never affected, which is why this came and went.
- A deployment with no mailbox configured no longer reports mail it never sent. Missing SMTP credentials degraded to the console provider on every runtime, and that provider reports success — so `EMAIL_LOG` recorded `sent`, and an administrator inviting a facilitator or speaker was told the invitation went out while nothing left the isolate. This is how the three `SMTP_*` secrets stayed unset in production unnoticed. On the Workers runtime a missing mailbox is now a failure: the invite answers `502` and the account it half-created is cleaned up so the address can be invited again, and ticket mail records a failed row. `pnpm dev` still logs to the console, where no socket exists either way and nothing is wrong.
- The tickets page renders again. Ticket rows carry their event under `EVENT`, but the card read `EVENTS` and dereferenced it without a guard, so the page threw for anyone actually holding a ticket. The same drift between what the API returns and what the client expected left the payments page showing "Unknown" for every event, ticket cards never showing a paid time, and four list views keyed on columns that do not exist — audit logs, email logs, payments and tickets all key on `id`.
- Assigning a speaker to an event works. The dropdown keyed its options on a column the API does not return, so the submitted value was not a number and every assignment was rejected as invalid. The same missing value meant speakers already on the event were never removed from the list, and every name displayed as "Speaker #undefined".
- Pages no longer sit on a loading spinner that never resolves. `/staff/courses`, the check-in kiosk, payments, checkout, event registration and room access each gated their data fetch on a session flag renamed to its opposite, so the fetch ran only while the session was still loading and was skipped once it was ready.
- The events list no longer flashes "No events found" before the events appear. A superseded request cleared the loading flag while the list was still empty, so the empty state rendered until the live request landed.
- Event cover images load for signed-out visitors. Covers are stored as `/api/storage/...` URLs and the middleware required a session for all of `/api/*`, so every cover on the landing page and the events list was answered `401`.
- Events can be created with a price, venue address, description and currency. The form collected five of the ten columns the API accepts, so every event created through the interface was free — and stayed free, because the edit form was missing the same five fields. A one-sided time range is now rejected in the form rather than arriving as an unexplained failure.
- Signing out no longer reports "Access Denied". Guarded pages treated a missing session as a permission failure, so logging out while on a staff page redirected to the denial screen instead of home.
- Event cards on the home page link to their event. The card read an id field the API does not return, so every link pointed at `/events/undefined`.
- The events listing and event detail pages load for signed-out visitors again. The middleware treated every `/api/*` route as protected, so an anonymous browser's fetch of `/api/events` was answered `401` before the handler ran, even though those handlers were built to serve published events to callers without a session. Public GETs on the event endpoints now pass through, with the handlers still filtering out drafts and every write staying behind the role guards.
- Sessions survive a token refresh. The middleware rebuilt its response once per cookie, so each write discarded the one before it and the browser was left holding part of a chunked auth token — presenting as a random logout. Refusing a request no longer drops the cookies either, which is what cleared an expired session, so a stale token could previously fail the same way on every retry. Responses that carry a refreshed session are now marked uncacheable, since a shared cache could otherwise replay one visitor's session to the next.
- Deleting an event now deletes its course material. Asset and video paths were collected and then discarded: the single cleanup call only ever targeted the `event_images` bucket, so every deleted event left its uploads orphaned in storage.
- Attendee search returns matches again. The filter named embedded columns at the top level, which PostgREST does not apply, so searching a name or email quietly returned nothing. Search terms are now escaped as well — an underscore in an email address matched any character, and a comma silently split the filter.
- QR check-in works again. Every scan returned "Invalid QR token" because the ticket lookup joined the user through the wrong column, so the query errored and the ticket was reported as missing.
- Inviting a member now invites them. The organization invite validated the form, wrote an audit entry and reported success without contacting anybody or creating anything — the invited person was never told, and no account existed for them to use. An invitation now goes out over the same mail server as the ticket emails, and accepting it grants the role they were invited as instead of dropping them in as an attendee. The message is built by the application rather than by Supabase, so it matches the other emails and its link stays on the project's own domain.
- Chat message senders, the event attendee list, and email log recipients load again — all four affected queries shared the same fault.
- Course pages load again. Three modules deleted during an earlier refactor left their importers behind, which broke the production build outright.
- The landing page shows the current events. It was prerendered at build time, so its "upcoming events" list was a snapshot taken at deploy: a newly published event never appeared and a finished one never left, until someone redeployed. It now renders per request. This also removes the build's dependency on a reachable database, which is what was failing the Build and Lighthouse jobs.
- Facilitator, admin and super admin accounts no longer see the speaker bio and designation section. Those settings live on the speaker row, but the account settings hook and the profile endpoint both checked the role with a minimum-role test — which every role above speaker also passes. Both now require the exact speaker role.

### Changed

- The landing page lists upcoming events as full cards — date, time, venue and cover art — instead of the bare title-and-date boxes it used to render, and the attendee home shows the same card grid at the same full-width spacing. The two pages previously drifted: the landing page hand-rolled its own minimal markup while the attendee home used the shared card component, and the home's cards ran edge-to-edge under the hero. Both now share one `EventGrid` so a change to the card design lands in a single place.
- General support is now a case queue. Every support session carries a global sequential case number — `CASE-10042` — shown in the attendee's chat header, and the staff inbox is a queue instead of an open floor: a case sits unclaimed until an admin claims it, and only the handler can reply, so two staff members can no longer answer the same attendee at once. The handler releases the case or ends it for good; the attendee starts a new one. Event support keeps its old immediate-reply flow, to be reworked separately.
- Course material is owned by the team running an event, not by whoever created the course. The `COURSE.created_by` column is gone — "who made this" still lives in the audit log's `course.created` event — and a course is managed by everyone assigned to its event: assigning a facilitator or speaker to the event is what grants authoring. Admins reach any course; deleting one is reserved for facilitators and admins, so an assigned speaker can still write material but cannot take the course down. Uploading course assets or videos used to need only the facilitator role, letting any facilitator write into any course, and the stored path was assembled from `course_id`/`module_id` the browser sent — which the builder was sending wrong anyway. Uploads now require an assignment to the lesson's event, and the path is derived from the lesson's own module and course ids with the client filename reduced to its basename, so neither the ids nor a path smuggled into the filename can redirect an upload outside its lesson. Flipping a Q&A lock is gated the same way, so an unassigned speaker can no longer freeze any module. The staff course authoring UI matches this policy: the admin courses table dropped its "Created By" column, since the column no longer exists, and the staff event page no longer offers a "Create Course" button to facilitators who are not assigned to that event — the button always failed with a 403 under the new policy. Authoring is shown only to the admin, the event's assigned facilitators, or its assigned speakers; everyone else sees the read-only course summary.
- Published event covers are served with a shared-cache lifetime, since they are the same bytes for every visitor and are rendered on pages anyone can read. Responses that depend on who is asking keep the `private` no-store header described above.
- Creating and editing an event share one form, so a field can no longer be added to one and forgotten in the other — which is how the two drifted apart.
- Uploaded images are compressed with WebAssembly instead of sharp. sharp binds to libvips as a native Node addon, which cannot load in the V8 isolate Cloudflare Workers runs, so it blocked deployment there outright. Uploads whose longest edge exceeds 1600px are now scaled to fit, which is invisible at the sizes the app displays — covers render around 350px wide — and is where most of the saving comes from: a 3200px camera JPEG drops from 393KB to 51KB, against 162KB for the quality change alone. JPEGs are still re-encoded at quality 80 on top of that. PNGs within the cap are stored as uploaded, since re-encoding one at its original size returns identical bytes; sharp used to quantise their palette instead. **Originals are not retained**, so a full-resolution upload cannot be recovered later.
- Migrated from Clerk to Supabase Auth. All auth logic centralized in `src/modules/auth/`.
- Old staff-related pages moved under `src/app/staff/` namespace; route protection updated accordingly.
- All API routes updated: `auth()` from Clerk replaced with `requireAuth()`/`requireRole()` from auth module.
- All client components updated: `useUser()`/`useClerk()` replaced with `useSession()` from auth module.
- Middleware rewritten to use `@supabase/ssr` for session management.
- Staff login page merged into unified sign-in page (role-based redirect).
- `pnpm test` now runs once and exits; `pnpm test:watch` is the watch mode. `AGENTS.md` asks contributors to run the tests before committing, which previously dropped them into a watcher.
- `prettier`, `vitest` and `eslint-config-prettier` moved out of `dependencies`. They were shipping to production, and separating them is what lets the audit block on production advisories while treating dev-only ones as advisory.
- `postcss` and `sharp` pinned above their advisories through pnpm overrides, clearing three high-severity findings that reached production through `next`.
